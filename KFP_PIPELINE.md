# Kubeflow Pipelines demo

[`kfp_pipeline_demo.py`](kfp_pipeline_demo.py) defines a three-step machine-learning pipeline with the KFP SDK 2.18.0. It can compile a pipeline package (`synthetic-pipeline.yaml`) and run the components **locally** for a first check. Running this Python file does not submit a job to the K3s cluster; a KFP backend must be installed and the package submitted before Kubernetes pods run the pipeline.

## Why K3s was installed

K3s provides the **Kubernetes cluster** for a later remote pipeline run. The local run completed so far used `local.SubprocessRunner()`: KFP started temporary Python subprocesses on this machine and wrote results to `local_outputs/`. That run did not use Kubernetes.

To use K3s for this demo, the next stage is to install a **KFP backend** on the cluster. The backend accepts `synthetic-pipeline.yaml`, creates Kubernetes pods for `generate-data`, `train-model`, and `evaluate-model`, and exposes their run status through a KFP UI and API. K3s alone supplies Kubernetes; it does not include that KFP backend.

```text
Completed local path: Python file → KFP local subprocesses → local_outputs/
Next cluster path:    pipeline YAML → KFP backend on K3s → Kubernetes pods → run results
```

Installing K3s was preparation for the second path. It was not required for the local test that produced 76.67% accuracy.

## What the pipeline contains

```text
generate_data → train_model → evaluate_model → accuracy
       Dataset ───────┘  Model ───────┘
```

1. `generate_data` creates 600 synthetic labeled examples with 10 features and writes `(X, y)` to a KFP `Dataset` artifact using `joblib`.
2. `train_model` reads that artifact, trains logistic regression on the **first 480** examples, and writes a KFP `Model` artifact. The pipeline's `c` parameter controls regularization; the local run uses `c=0.5`.
3. `evaluate_model` reads the dataset and model, predicts the **remaining 120** labels, and returns accuracy as a `float`. A KFP artifact is a file passed between steps; the accuracy is a small scalar output.

The components declare a `python:3.11-slim` base image and pinned `scikit-learn` and `joblib` packages for container execution. The local subprocess runner prepares its own temporary Python environments for the components.

### What `c` means

The pipeline passes `c` into `LogisticRegression(C=c, max_iter=1000)` in `train_model`. Scikit-learn's `C` is the **inverse of regularization strength**. Regularization discourages large model weights: a smaller value such as `0.5` applies stronger regularization than `1.0`, while a larger value applies weaker regularization. Changing `c` changes how the model is trained; it does not change the generated dataset or the train/test split.

`c` is a setting chosen **before training**, not an accuracy or F1 score. The compiled YAML defaults to `c=1.0`, but the completed local run explicitly used `c=0.5` and scored `0.7667` accuracy (92 correct predictions out of 120). Set `c=0.5` when starting the cluster run if you want a direct comparison. That one result does not establish which `c` value will perform best on other data.

## What happens when you run the Python file

The `@dsl.component` functions define the three reusable steps, and `@dsl.pipeline` connects them. Defining the pipeline does not train a model. The code in the script's `__main__` block then does these actions in order:

1. **Compile:** `compiler.Compiler().compile(...)` translates the Python pipeline definition into `synthetic-pipeline.yaml` in the current directory.
2. **Optionally stop:** With `--compile-only`, the script exits after writing the YAML.
3. **Run locally:** Otherwise, `local.init(runner=local.SubprocessRunner())` starts a local runner, and `training_pipeline(c=0.5)` executes `generate_data`, `train_model`, and `evaluate_model` in dependency order. The final printed value is evaluation accuracy.

The YAML is the **pipeline recipe**: it records component code and settings, the task graph, artifact connections, and the default pipeline parameter `c=1.0`. It is generated by the Python file and can be regenerated. It does not contain a trained model or accuracy result; those appear only after a run executes. The local run overrides the default with `c=0.5`.

Local execution runs on this machine through subprocesses. It does not create K3s pods. A run on K3s requires a KFP backend and a separate submission of the compiled package.

## Compile or run locally

From the project root, with `.venv` active:

```bash
python3 kfp_pipeline_demo.py --compile-only
```

This writes `synthetic-pipeline.yaml` and exits. The YAML is a **KFP pipeline package** for a KFP backend, rather than a normal Pod manifest for `kubectl apply`.

Because the learner ran the command from `/home/allen/mlops-quickstart`, the relative output path created `/home/allen/mlops-quickstart/synthetic-pipeline.yaml`. Compilation finishes before local execution begins, so pressing Ctrl+C during `generate-data` did not undo the YAML.

To compile and run all three components on this machine:

```bash
python3 kfp_pipeline_demo.py
```

The script prints an explanation before starting local execution. The local runner may be quiet while it creates a temporary virtual environment and installs dependencies. Once it finishes, it prints the evaluation accuracy. The local run does not need the K3s cluster or MLflow server.
